# Changelog

Versions follow `package.json` and `tealbrick.manifest.json` (product id `rules`).

## 0.3.1 - Unreleased

Calls from product X (decision C237; Lane D review items S4-3 and S4-5). Needs bridge >= 0.2.2, which sends `HookCallInfo.caller.product` (spec 0.1.45); on older bridges a deny/hold rule with `callerProducts` applies to every app call and an allow rule with it never matches (see "Fail closed"). `requires.bridge` stays 0.1.17: nothing else needs the newer bridge, and an older one only makes these rules stricter. The version in `package.json` and the manifest is bumped by a separate chore PR.

### Added
- Match criterion `callerProducts` (list of product ids, unique, at most 50; `[a-z0-9][a-z0-9_-]*`, at most 40 characters) in every rule schema of the manifest (`rules_set`, `rule_draft_submit`, `rules_list`, `rules_get`, the drafts, `rules_preview` candidate). It matches only an APP caller whose VERIFIED product is listed. The product is the one the bridge sends on the hook call (`caller.product`, from its signed config), never an input field, a context field, a manifest name or an instance id. An AGENT never matches a rule that names `callerProducts`, whatever the decision (deny, hold or allow): an agent is not a product.
- `rules_preview` takes `call.caller.product` for an app caller and answers `callerProductUnavailable`; the step text says when a rule applied or was skipped for that reason. `rules_explain` adds `callerProductUnavailable` per decision, next to `fleetUnavailable`. `decisions_list` adds `caller.product`. `rules_list` adds `catalog.productIds` (the editor's app picker).
- Editor: the field "Calls from apps" (chips of the catalog's apps; an app the catalog does not list stays visible while a rule names it), the rule list line "calls from app ...", the dry run caller "An app" with its product, and the notice "The calling app's product can't be verified, ...". The Decisions page names an app by its product and says when it was not verified.
- Migration `migrations/0006_caller_product.sql`: nullable `decisions.caller_product` and an index on it. No row changes; no down migration. A failed update is rolled back by the SDK pre-update snapshot.

### Changed
- `rules_explain` for an app caller reads its decisions by its verified product (S4-3): every instance of the product, so a reinstall keeps the history. Rows recorded before 0.3.1 have no product and are found by the instance id. An app with no verified product reads by its instance id only. An agent reads by its agent id as before.
- The decision trace records the verified product of an app caller (`decisions.caller_product`). The context-phase trace of a narrowing now carries the same `fleetUnavailable` and `callerProductUnavailable` flags as the before-phase trace.
- Writers stay strict (L24): a rule is refused when `callerProducts` holds an id that is not a product id, lists an id twice, or is combined with a field that can never match an app: `agents` that lists only `agt_` ids (an app is listed by its instance id `ins_...`), `modes`, or `callerTeams`. Stored rules and drafts are read as they are (they simply never match); the Rules page flags them "never matches".
- The product validity rule (`validProduct`) lives in `src/engine.ts` only; the draft identity, the hook facts, the dry run and the writers share it.

### Fail closed (C237)
- An app caller with an absent or invalid product (a bridge older than 0.2.2, a caller the bridge cannot map, or a value that is not a product id) is handled like unavailable Fleet facts, with the same machinery and severity order: a deny or hold rule that names `callerProducts` APPLIES (flag `closedOnProduct`; trace and `rules_explain` detail `callerProductUnavailable: true`), an allow rule that names them does NOT apply and its narrowing still applies (merged strictly, as for a Fleet gap). The decision is the highest severity among the closed deny/hold rules before the first rule that matches without unavailable facts, together with that rule.
- Seeded fuzz tests (30 000 and 40 000 random rule sets) check that an app without a product is never decided less strictly, and never narrowed less, than with any product; an agent is decided as if the product rules did not exist.

### Caller identity (S4-5)
- An app caller is identified by its verified product everywhere in Rules: draft keys (0.3.0), `callerProducts` rules and `rules_explain` (0.3.1). Names are labels only. An agent is identified by its agent id and never matches a product rule.

## 0.3.0 - Unreleased

Rules 0.3.0 reads `directory_feed`, which Governance 0.2.0 adds; against Governance 0.1.x it finds no such op, so its Fleet facts are unavailable (see "Fail closed").

### Added
- Match criterion `callerTeams` (list of Governance team ids): the CALLING agent is a member of one of them.
- Match criterion `onBehalfOf.trust` (list of `unreviewed`, `trusted`, `limited`, `blocked`): the trust of the claimed requester, read from the feed by contact id (claim kind `person`), canonical handle (`channel_sender`) or agent id (`agent`). A requester the directory does not know (unknown handle or id, a contact or agent the producer left out) is `unreviewed`. An unverified claim may only narrow (C82): a deny or hold by trust applies, an allow by trust never beats a later deny.
- Both criteria are in every rule schema of the manifest (`rules_set`, `rule_draft_submit`, the drafts, preview), `rules_preview` (answers `callerTeams`, `trust`, `fleetAvailable`), the step explanations, `fleet_status` (`available`), the editor, the rule list and the Teams page.
- Operation `draft_status {draftId}` (agent audience; an app with a companion grant may call it): `{draftId, status, submittedAt, decidedAt, ruleCount}`. It answers only for drafts the caller itself submitted; any other id, and an id that does not exist, give the same `not_found` (404).
- `rule_draft_submit` records `source` on the draft: `{kind: "agent"}` or `{kind: "app", product, name, instance}`. `product` is the VERIFIED `ctx.caller.product` of the app caller (SDK 0.1.27, C236); `name` is the app's own manifest name and only a label. An app caller is identified by its product everywhere in Rules (see "Caller identity"). The Drafts page says "proposed by the app <product> (called itself <name>)"; a draft stored before 0.3.0 has no product and says "proposed by an app named <name> (unverified)".
- `rules_explain` adds `fleetUnavailable` per decision (true when a deny or hold rule applied only because the Fleet facts were unavailable).
- Contract files `test/contracts/fleet.directory_feed.1.schema.json` and `.json` (spec tag `spec-v0.1.42`, sha256 in `test/contracts/PROVENANCE.md`, same bytes as the Governance copy); the runtime schema `src/contracts/fleet.directory_feed.1.schema.json` is a second byte copy (the image has no `test/`). Tests run every fixture through the real reader.
- Migrations 0003, 0004 and 0005 (`migrations/0003_feed.sql`, `0004_feed_sets.sql`, `0005_feed_holders.sql`): tables `fleet_trust` (per key: the holders' trust set and `all_active`), `fleet_sync.usable`, `fleet_members.active`, `drafts.source`. They clear the 0.2.x Fleet copy (its `person:<id>` keys are gone) and forget the revision, so the first read after the update is a full one. Rules, drafts and decisions stay. There is no down migration; a failed update is rolled back by the SDK pre-update snapshot.

### Changed
- The companion is `fleet.directory_feed` (read), not `directory_get`. Every answer is validated against the vendored schema (`validateAgainstSchema` of `@opt2-tealbrick/manifest`) and every handle must satisfy `normalizeHandle(h) === h`. A mismatch is a refusal: the error shows in `fleet_status`, the copy is cleared, nothing of the answer is read. An `unchanged` answer is believed only for the `sinceRevision` that was sent. The 503 `feed_too_large` is transient (the last copy stays up to 10 minutes).
- Mapping: keys are `agent:<id>`, `contact:<id>` and `handle:<canonical>`; a handle can have SEVERAL HOLDERS. A holder is active unless it is blocked, a departed contact or a removed agent (a paused agent is active; a blocked agent is not). Deny and hold rules match a key when ANY holder matches (membership of the team, trust in the list), so blocked, departed and removed members and members the producer left out still count for them. Allow rules need EVERY holder active and matching: a handle shared by an active and a blocked or departed contact never opens an allow rule, and a gone holder never satisfies an allow by trust. Trust is the SET of the holders' raw trust values (deny/hold keep the raw value, a departed `trusted` stays `trusted` for them); a requester the directory does not know is `unreviewed` and active. Live team facts (`fleet.requesterTeams`) never open an allow rule for a requester the copy knows to be gone (a gone holder, or a member that counts nowhere). A team, contact or agent id listed twice is a `feed_invalid` refusal.
- Handles use the one shared `normalizeHandle` of `@opt2-tealbrick/manifest` 0.1.19 (G-4); a claim id that is not a valid handle has no handle (no match, never the raw text). The local normaliser is gone.
- UI and manifest text say "Governance" where they said "Organization Plane".
- Dependencies: manifest 0.1.25 (was 0.1.18), miniapp-sdk 0.1.31 (was 0.1.25), conformance 0.1.22 (was 0.1.18); ui 0.2.4 unchanged. Lockfile integrity re-pinned (`tb-ci pin-tarballs`). Conformance 0.1.19 added `A12.caller_product_verified`; 0.1.22 passes.

### Caller identity (C236, SDK 0.1.27)
- An APP caller of an agent-audience op (`rule_draft_submit`, `draft_status`, `rules_explain`) is identified by `ctx.caller.product`, the product id the Portal-signed slice gives for the grant's instance; never by `ctx.caller.name`, a manifest name or an input field (names stay display labels). One helper (`identity` in `src/app.ts`) decides it.
- An app caller with no verified product fails closed: nothing that depends on a product applies to it. Its draft is still accepted (a draft is only a proposal the owner must approve, C84, and conformance A12.companion_inbound requires the op to run), but it is keyed by the app's instance id, records no `product`, and the Drafts page shows it as unverified. It cannot read a draft of a verified product, and a verified product cannot read its drafts. A name, even one equal to a product id, never gives a product.
- Drafts from an app are keyed by product: `submitted_by_id` is the product (it was the instance id), `draft_status` answers only for the same product (a reinstalled app keeps its drafts; another app with the same name gets `not_found`), and the limit of pending drafts counts per product. Drafts stored before 0.3.0 keep their instance id, so `draft_status` cannot show them to an app (fail closed); the owner still sees and decides them.
- The pending-draft cap counts per type and identity. All apps with no verified product share ONE cap (a reinstall gets a new instance id and must not reset it); a verified product, an agent and an app never share a cap. A product that is not `[a-z0-9][a-z0-9_-]*` of at most 40 characters is treated as no verified product (defence in depth).
- `rules_explain` for an app reads the decisions recorded under its (verified) instance id: the before hook gets the instance id of an app caller and no product (`HookCallInfo.caller` has `type`, `id`, `mode`; spec 0.1.44), so decisions cannot be keyed by product. A rule's `match.agents` accepts `agt_` and `ins_` ids and matches the hook's verified `caller.id`, not a name. Rules 0.3.0 has NO "calls from product X" criterion: the pinned spec 0.1.44 has no product on the hook call. Spec 0.1.45 adds `HookCallInfo.caller.product` (bridge 0.2.2 and newer); the criterion (a new match field in every rule schema and the editor, deny/hold applies and allow does not match when the product is absent) is planned for Rules 0.3.1 on miniapp-sdk 0.1.28.
- No inbound operation of Rules trusts that a caller is Governance. The Governance feed is an outbound `callApp("fleet", "directory_feed")`, addressed by product; its answer is validated against the vendored schema, not trusted by the caller's name.

### Fail closed (C230, C236)
- Severity: while the facts are unavailable the decision is the HIGHEST severity (deny > hold > allow) among the closed deny/hold rules before the first rule that matches without any Fleet fact, together with that rule, so a later deny beats an earlier closed hold and the result is never less strict than with the facts (a seeded fuzz test of 40 000 random rule sets checks decision and narrowing).
- Before, an empty or old Fleet copy made team rules match nobody, so a deny or hold rule that names teams stopped applying. Now, while the Fleet facts are unavailable (never read, refused or invalid, or no successful read for 10 minutes), a deny or hold rule that names Fleet facts (`callerTeams`, `onBehalfOf.teams`, `onBehalfOf.trust`) applies, and an allow rule that names them does not. Other criteria still decide first, and `onBehalfOf` still needs a claim. The A2A-9 rule stays: stale membership is never used.
- An allow rule skipped for that reason still narrows: while the facts are unavailable the narrowing of every skipped allow rule that precedes the decisive rule is merged strictly into the verdict (so the call never gets a wider result than with the facts), emitted as `rules.narrowing` and recorded. The before phase pins the narrowing it decided per call id (read calls; at most 20 000, 92 s); `rules_filter` redacts by that pin. With no pin (restart, expiry, eviction) it applies the strictest narrowing that could apply.
- The decision trace of such a call carries `detail {fleetUnavailable: true}`; the dry run says so per rule. The Rules pages show "Governance data unavailable — team rules apply strictly".
- Operations note: an owner who has deny or hold rules on teams sees them apply to every matching call while Governance is down or older than 0.2.0. That is the intent.

### Sync
- A big answer is validated in slices and mapped with a yield to the event loop every 4 000 units of work (200 teams x 350 members: longest block about 17 ms; the schema maximum of 500 teams x 4 000 members with 16 handles per contact needs about 2 s and 1.5 GB, with GC pauses up to about 100 ms; 500 x 4 000 with one handle: 23 ms). `syncFleet` never rejects: if the database refuses the write that clears the copy, the in-memory copy is dropped (the facts are unavailable) and the error is kept in memory.
- The copy is written in transactions of at most 4 000 rows with a yield between them (measured for 200 teams x 350 members: longest transaction under 6 ms; the whole write about 0.2 to 0.4 s), the gate's index is built during the write, and a crash half way leaves the copy unusable (fail closed). `markFleetStale` during a read triggers one more full read.

### Not in this release
- Agent trust (`agents[].trust`) is not a match criterion.
