# Changelog

Versions follow `package.json` and `tealbrick.manifest.json` (product id `rules`).

## 0.7.0-dev.2 - DEV pre-release (C380)

### Fixed
- The company floor now sees a recipient. The bridge sends no `target.recipients` yet, so a DM to a stopped person passed the floor (QA A29). The floor reads who Connect's send ops name from the call's own input: `buzz_dm`, `channel_dm`, their first-contact forms, `channel_send`, `channel_edit`, `channel_react`, and the arguments of connected send tools, read as Connect's first-contact gate reads them. `channel_reply` names nobody in its input: Connect's own bar covers it. ## 0.7.0-dev.1 - DEV pre-release (C380, not for stable until the owner decides D2, D3)

### Added
- The company floor (C380, overrides C84, DEV only until the owner decides). One line before every rule, in all modes: a caller agent, an acting agent, a claimed requester or a known recipient that Governance lists as stopped (suspended, leaving, closed, not started yet, blocked; on an older Governance: blocked or departed) is refused. The caller reads only "Refused by company policy"; Decisions keeps the full reason. It reads its own table, written only by a full valid read of the feed, so a paused Governance, a lapsed licence, an outage, an invalid answer or a restart do not lift a stop. Exempt: `rules_explain`, `draft_status`, `floor_status`. Owner actions are never seen by hooks.
- `floor_status` (Governance only): version, feed revision, entries, last gate time. `floor_list`, `floor_clear` (owner): the Company floor card on the Rules page lists who is stopped; Clear is the way out when Governance is gone or cannot be trusted. Every clear is recorded.
- System line: Governance reads who has access (`access_list` of Connect, Knowledge, Task Board, Evolving Workflows, and Rules `floor_status`). `access_revoke` is never covered.

### Changed
- `directory_feed` is read with `accept: ["agent_handles", "lifecycle"]`. Schema `fleet.directory_feed.1.lifecycle` (spec 0.1.89).
- A rollback of Governance to a release with no lifecycle facts does not lift a lifecycle stop: the owner clears it on the Rules page.
- `upgradeFrom` is `<0.7.0`. `requires.bridge` stays 0.2.13.
- **On update:** entries Governance already marks blocked, and departed contacts, start to be refused at the first read of the feed. List them before any promotion.

### Fixed: adversarial review of 0.5.0 (C373, REVIEW-0.5.0)
- S2-1 English parser and negation: "Do not allow Hermes to pay" proposed allow money, "Hermes may send messages but not pay" allow outward + money. Negation and exception words are now read exactly or not at all: "do not allow", "don't permit", "should not", "never let", "may not" … refuse; a fragment that starts with not / without / except / other than / apart from and names only effects ("…, not pay", "… without paying", "Allow everything except money") refuses those effects BEFORE the allow of the same sentence; any other negation (with a name, a hold, a condition, "unless", "doesn't" …) sends the sentence to `unmatched`. A negated fragment never inherits an allow.
- S2-2 team rules and Rules' own Governance read: a deny/hold `callerTeams` rule applied to APP callers while the Governance facts were missing, Rules' own `fleet/directory_feed` read included, so the facts never came back. Teams are agent facts: an app never matches a `callerTeams` rule (like `callerTrust`), and a rule that matches the feed read ONLY because the Governance facts are missing never applies to it (defence in depth; a fuzz test checks every writer-accepted rule set in all three modes). Only a rule that names the read (`products: ["fleet"]` or `callerProducts: ["rules"]`) can stop it; the UI warns on such a rule: "This rule cuts Rules off from Governance".
- S3-1 feed without agent handles: after a 400 to `accept` (or with a Governance older than 0.3.0, or after a restart before the first full read) the copy has no agent handles, so a handle's holders may miss an agent. While that is so, every recipient a call names is UNKNOWN: deny/hold recipient rules apply, allow recipient rules do not. Caller and claim teams and trust stay usable.
- S3-2 placement of composed holds: deny before hold before allow relative to the existing rules. A composed hold goes after every existing refuse rule (it never weakens one) and before every existing allow; no room → unmatched with a hint. No composed rule ties with an existing rule of another decision (an allow at priority 0 leaves no room for a refuse or hold).
- S3-3 priorities at approval: `draft_decide` approve places every draft rule again against the CURRENT rules, active and inactive (`src/placement.ts`): an allow after every refuse or hold rule it could overlap, a hold after every refuse rule it could overlap, never on a tie; a refuse keeps its priority. No room → 409 `draft_no_room`. `drafts_list` / `draft_decide` carry `places[]` (final priority, from, why) and `placeProblem` for pending drafts; the Drafts page shows the final priority. The English box counts inactive rules too. "Allow always" (D12) counts inactive refuse rules and treats a tools rule as covering its `__` variants.
- S3-4 model drafter: the model only ADDS rules (every parser rule stays, a repeat is dropped, a model allow with an empty match is refused); agent, team and app names go into the prompt as quoted JSON lists, control and format characters removed, 64 characters each.
- S4-1: a `target.tool` that is no catalog tool name (one `__` variant suffix allowed) counts as absent (a dynamic op then fails closed for deny/hold tools rules).
- S4-3: a channel-sender claim is traced as `{kind, handle: true}` (its id is a handle); the feed error for a non-canonical handle names the contact or agent, never the handle.
- S4-4: a model draft failure is logged as a fixed word (`timeout`, `answer_not_json`, `http_<status>`, `error`), never its message (an undici error can carry the provider URL with userinfo).

### Sync
- A big answer is validated in slices and mapped with a yield to the event loop every 4 000 units of work (200 teams x 350 members: longest block about 17 ms; the schema maximum of 500 teams x 4 000 members with 16 handles per contact needs about 2 s and 1.5 GB, with GC pauses up to about 100 ms; 500 x 4 000 with one handle: 23 ms). `syncFleet` never rejects: if the database refuses the write that clears the copy, the in-memory copy is dropped (the facts are unavailable) and the error is kept in memory.
- The copy is written in transactions of at most 4 000 rows with a yield between them (measured for 200 teams x 350 members: longest transaction under 6 ms; the whole write about 0.2 to 0.4 s), the gate's index is built during the write, and a crash half way leaves the copy unusable (fail closed). `markFleetStale` during a read triggers one more full read.
