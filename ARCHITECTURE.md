# Rules & Approvals (Tealbrick mini app): architecture

State: verified against the repo on 2026-10-17. Claims cite paths in this repo. Anything not verified is marked UNVERIFIED. For the whole system see the system `ARCHITECTURE.md` and `SYSTEM-OVERVIEW.md`.

## Common app pattern (verified for this repo on 2026-10-17)

- **Runtime**: Node 24, TypeScript run through `tsc` to `dist/`, UI built by `scripts/build-ui.ts` (no bundler; content-hashed `assets-<hash>/`). The app is started by `startApp` from `@opt2-tealbrick/miniapp-sdk` (`src/main.ts`).
- **Dockerfile**: two stages on `node:24-slim` pinned by digest, `pnpm install --frozen-lockfile --ignore-scripts`, `pnpm run build && pnpm prune --prod`, the manifest also copied to `/opt/tb/tealbrick.manifest.json` (the `tb-exec` default), `USER node`, no `VOLUME`. The SDK drops root to uid 1000 itself when the platform starts the container as root (Railway volumes are root-owned).
- **Data**: one SQLite file `TB_DATA_DIR/app.db` owned by the SDK. App tables use their own prefix; SDK tables use `tb_*`. On Railway there is ONE volume per service: the backup directory is `<data mount>/backup`, so the volume size is data plus backup (C28).
- **Migrations**: `migrations/NNNN_name.sql` (or `.ts` exporting `up(db)`). The SDK enforces forward-only: gap-free from 0001, one transaction each, sha256 recorded in `tb_migrations`. A changed, missing, misnamed or `down` migration stops the app with `migration_invalid`.
- **Backups and restore**: SDK cron runner writes `tb-backup-<UTC>.tar.gz`; export `tealbrick.export/1` never carries the instance key, KEK, keys, secrets or sessions. Restore at next boot with `TB_RESTORE_FROM`.
- **Authorization**: the bridge gates (`gate()`); the SDK decides (`authorize()`): run, hold or refuse. Holds and receipts live in the app's own `tb_receipts` table. Raw call input is never stored, only a digest.
- **Manifest** `tealbrick.manifest.json` is the only source for operations, scopes, settings, hooks, companions, skills, runtime hints, backups and UI paths. Schema `tealbrick.miniapp/2`, `sdkMajor 1`, `source.license Apache-2.0`. Agent ops become MCP tools `<product>__<op>`. Person ops are owner UI only.
- **Generated**: `gen/` (openapi, kit, docs, railway) is produced by `tb-gen` and is not committed. The typed client kit is built into `dist/kit` and imported as `#kit` in apps that have one.
- **Standard UI pages** (from the kit `AppShell`): Holds, Receipts, Agents and scopes, Keys (where the app has keys), Backups and export.
- **Licence files**: `LICENSE` (Apache-2.0), `NOTICE`, `THIRD_PARTY_NOTICES.md`. The brand mark and app art are Tealbrick artwork and are not Apache-licensed.
- **Private by design**: no public address. Only the bridge is public.

## Rules & Approvals: what it does

Rules declares hooks on all products. **If Rules is down, every agent call in the workspace is refused (`hook_failed`), reads included.** A hook leaves the gate only by explicit owner action, never by a transient state (C117, L33).

Rule shape: `title`, `active`, `priority` 0 to 1000 (lower first), `match` {agents, modes, products, operations, `tools`, effects, `callerTeams`, `callerProducts`, `onBehalfOf` {teams, ids, kinds, trust}}, `outcome` {decision allow, deny or hold; reason up to 280 characters}, optional `narrowing` {`memoryTags` {anyOf, noneOf}, `deepDatasets` {anyOf, noneOf}}. The first matching active rule decides. No match: the workspace default mode decides (section "Default mode"). Outward, destructive and money calls are always recorded. An unverified `onBehalfOf` claim may only make a decision stricter (C82).

## Operations (from `tealbrick.manifest.json`)

17 operations. No hold families on its own ops (Rules produces holds on other apps with family `policy`).
- Agent (an app with a companion grant may call them too): `rules_explain` (read), `rule_draft_submit` (write; draft only; records who proposed it: `source` {kind `agent` or `app`, product, name}), `draft_status` (read; answers only for drafts the caller itself submitted, any other id is `not_found`, the same as a missing one).
- Person read: `rules_list`, `rules_get`, `rules_preview` (dry run), `decisions_list`, `drafts_list`, `fleet_status`, `rule_compose` (C373 J3: the owner's English → proposed rules, no state), `mode_get` (C373c: the default mode, its history and the system lines). Person write: `rules_set`, `rules_delete`, `rule_compose_save` (C373 J3: the proposal as a pending draft, `source.kind` `owner`, idempotency required; it applies only through `draft_decide`), `rule_restore` (C373 Q-7: an earlier revision becomes current as a new `restored` revision; a deleted rule comes back; same writer checks as `rules_set`), `draft_decide`, `mode_set` (C373c: the default mode; looser needs `confirm: true`). `rules_list` rows carry `deleted`; `rules_get` revisions carry `change` `restored` with `from`.
- English box (C373, J3): `src/compose.ts` is a pure, deterministic parser (no model, no network) behind a `Drafter` seam (`rule_compose.drafter`: `parser` or `model`). The optional model drafter (`src/model-drafter.ts`) runs only when the parser left words unread, the bridge declares cap `model_roles` and SDK `modelRole("utility")` (else `"reasoning"`) resolves; it calls the owner's bound provider (OpenAI-compatible chat completions or the Anthropic messages API, 20 s timeout), parses the JSON answer and vets it like the parser's (plus `namesProblem`: only ids the directory lists); it is used only when it keeps at least as many rules, and any failure falls back to the parser with a note. The key is never logged or returned. Hooks never reach it. Names come from the agent directory (`events.agentsChanged`, kept in memory by `src/directory.ts`), the Fleet copy (team names) and the catalog (product ids plus a few display names). A name that is not found or that two agents or teams share is never guessed (the sentence is listed as not read, with close names). `vetProposal` runs the writer checks (manifest RuleSpec schema, then `ruleProblem`) on every drafter's rules; the parser drops a whole sentence when one of its rules is refused, and never proposes an allow rule from a partial reading. Composed refuse/hold rules get priority 10, allow rules 20. "Evolution's outward actions" / "calls from the Evolution app" name the app that makes the call (`callerProducts`).
- Writers refuse a rule that can never match (unknown app or op, person-only op, impossible effect, `tools` on a static op or on an app without a dynamic op) using the app catalog. An empty `anyOf` from an owner is refused (C115), for `memoryTags` and for `deepDatasets`. Writers also refuse an invalid or repeated `callerProducts` id and a combination of `callerProducts` with `modes`, `callerTeams` or `agents` that lists only `agt_` ids (an app call has none of them).
- Spec 0.1.68 (C336 RQ-2, with C325 and C330; specs#47): `match.tools` matches the bridge's `target.tool` (case-sensitive; an entry `x` matches `x` and its resolved variants `x__…` only, QA-RULES18-4; an entry containing `__` is refused at save; no other wildcard). Without `target.tool`: a static op never matches; a dynamic op (placed by the cached app catalog, `dynamic` fact; an op the catalog cannot place counts as dynamic) fails closed: deny and hold rules apply, allow rules do not, and `detail.toolUnknown` is recorded; `narrowing.deepDatasets` limits the datasets a data app may read. Both are fields of the rule JSON in the `rules.spec` column, so there is no migration: a stored rule without them reads as before. Rules only emits `deepDatasets` in `rules.narrowing`, with `v: 2` exactly when it is present (else `v: 1`); it never reads or filters dataset rows, and the after hook still redacts by memory tags only (a dataset narrowing is applied by the data app before it reads, SDK-API 18.5). The decision log keeps the tool name in `detail.tool` and shows it as `target.tool`.
- Dataset ids compare EXACTLY (case-sensitive, no trim). The comparison (`datasetsMatch`, SDK-API 18.5 rules 3 and 4: key absent passes; key present needs a non-empty id list, under `noneOf` as under `anyOf`; then `anyOf` needs every id in it and `noneOf` excludes; no lineage, rule 4a: derived datasets are listed explicitly) is a LOCAL copy in `src/engine.ts` with a TODO: no released @opt2-tealbrick/manifest carries the shared helper yet (0.1.31, pinned, is spec 0.1.64), and the copy is deleted when Rules pins the release that does (one mechanism, L1). The pins and the SDK types carry spec 0.1.64 shapes, so `target.tool` is read structurally (`toolOf` in `src/hooks.ts`, marked `spec 0.1.68`). The editor does not show "needs a bridge with `hook_tool`" (Core and the GUI do); SDK 0.1.37 and later give the app `ctx.bridgeCaps`, which a later release can use for that hint.
- Caller identity (S4-5): an app caller is its VERIFIED product (hook `caller.product`, bridge 0.2.2 or later; `ctx.caller.product` on ops), never a name; an agent is its agent id and never matches `callerProducts`. An app with no valid product fails closed with the same machinery as unavailable Fleet facts (`closedOnProduct`, trace detail `callerProductUnavailable`). `rules_explain` reads an app's decisions by `decisions.caller_product`, older rows by instance id. Product is identity (C237, accepted): two live instances of the same verified product share one `rules_explain` history; products, agents and unverified apps (by instance id) stay isolated from each other. Writers check `callerProducts` against the signed app catalog exactly like `products` (`catalogProblem`; no catalog = `CATALOG_MISSING`, `catalog_unavailable` 503), and `ensureCatalog` reads the catalog for it too.

## Default mode (C373c, since 0.5.0)

Martin's decision C373c: one workspace-wide mode for calls that match NO rule. `permissive` = allow (every release before 0.5.0 behaved so; a fresh install and an updated 0.3.2/0.4.x install start here, migration 0008), `verification` = hold, `closed` = refuse.

- **Where it acts:** only the no-match path of `evaluate` (`src/engine.ts` calls `modeVerdict` in `src/mode.ts`). A call that matches a rule is decided by that rule in every mode: an allow rule still allows with its narrowing, deny and hold rules decide as before. The fail-closed machinery for Fleet facts, products and tools is unchanged; an allow rule skipped for an unavailable fact leaves the call unmatched, so in Verification or Closed the mode holds or refuses it (stricter, never wider). An unverified on-behalf-of claim is evaluated with and without the claim rules as before (C82), both with the mode, so a claim cannot open a Closed workspace.
- **Answers:** Verification answers a normal Rules hold (family `policy`, "Needs owner review: no rule covers this call (Verification mode)"): the TARGET app holds the call and it shows in that app's Holds and in the operator Inbox (`tb.holds_pending`); the approved retry runs once, like any Rules hold. Closed refuses "Rules: no rule allows this call (Closed mode)". Without the hold verdict (old bridge) a Verification hold refuses (fail closed). Agents, app (companion) callers and Evolution engine calls all reach `rules_gate`, so the mode applies to all of them.
- **Speed:** the mode lives in a per-database cache (`src/mode-store.ts`) next to the rules cache; the gate does no extra query per call; `mode_set` refreshes it. A missing or damaged row reads as `closed` (fail closed; the migration inserts the row and a CHECK keeps the value valid).
- **Context and after hooks** evaluate without the mode (Permissive): a call reaches them only when the gate allowed it or the owner approved its hold, and it must carry the narrowing it would carry in Permissive mode, including that of skipped allow rules.
- **Changing it:** person op `mode_set {mode, confirm?}` (idempotency required). Looser (closed → verification → permissive) needs `confirm: true`, else 409 `confirm_required`; tighter needs none; the same mode again changes and records nothing (a replay is harmless). Every change is a `mode_changes` row (who, when, from → to); `mode_get` returns the mode and its history; `rules_list` returns the mode and the system lines. Agents cannot change it (person op).
- **Explaining it:** a mode hold or refusal is a decision trace with detail `{decidedBy: "mode", mode}` (an exemption that let a gated-effect call pass: `{decidedBy: "exemption", mode, exemption}`). A Permissive no-match trace is unchanged; a row with no rule and no `decidedBy` reads as Permissive (`traceDecidedBy`). `rules_explain` returns `decidedBy` (`rule`, `mode`, `exemption`) and `mode`; the Decisions page says "decided by … mode"; `rules_preview` returns the mode outcome (`modeNote`) and takes a `mode` to compare. When `rule_compose` (the English box) proposes an allow rule, its first note says what the mode does outside it (`composeModeNotes`).

### Built-in exemptions (the mode never holds or refuses these)

They act ONLY on the no-match path: an owner rule that matches such a call still decides it (an owner may deliberately refuse Rules' own feed read). Each is shown on the Rules page as a read-only "system" line (`EXEMPTIONS` in `src/mode.ts`).

1. **`rules-governance-feed` (required by C373c (a)):** caller type `app` with the VERIFIED product `rules` (the bridge's signed `caller.product`), target product `fleet`, op `directory_feed`. Why: Rules reads Governance through the companion grant, and the bridge runs every before hook on companion calls, Rules' own included (bridge `calls.ts` `hookMatches` has no self-exemption). Without it, Closed would refuse the feed read (the refusal clears the Fleet copy, so every team rule turns strict for good) and Verification would park it as a hold in Governance: a fail-closed loop that only the owner could break. Not exempt (tests fire on each): an app caller without a verified product (`ins_` id only, or a value that is no product id), another fleet op, another caller product, an agent, and Rules calling any other app.
2. **`inbox-owner-alerts` (the hold-notification loop):** caller type `app` with the VERIFIED product `inbox`, target product `connect`, ops `buzz_dm`, `buzz_dm_first`, `channel_dm`, `channel_dm_first` only (the ops Operator Inbox uses to DM the owner, opt2-tealbrick-inbox `src/alerts.ts`; its manifest companion lists exactly these four). Why: in Verification a mode hold reaches the owner's Inbox, and Inbox DMs the owner through Connect; that DM matches no rule, so the mode would hold it too: a new hold, another DM, another hold, without end, and the owner never gets the first alert. Closed would refuse every owner alert. Not exempt (tests fire on each): an app caller without a verified product, another product calling `buzz_dm`, Inbox calling another Connect op, an agent calling `buzz_dm`, the same op name on another app. An owner rule on Connect still decides these calls. The exemption is outward, so its calls are recorded with detail `{decidedBy: "exemption", exemption: "inbox-owner-alerts"}`.
3. **`rules-self-service`:** target product `rules`, ops `rules_explain`, `rule_draft_submit`, `draft_status` (any caller). Why: in Closed or Verification an agent must still be able to ask why it was stopped and to propose a rule; a draft changes nothing until the owner approves it (C84), and the two reads return only the caller's own rows. Without it, Closed cuts agents off from the only way to ask for a rule, and Verification would hold a draft that then needs a second approval.
4. **`platform-standard-ops`:** any target op in the reserved `tb.` namespace (manifest op ids can never contain a dot, so no app op can look like one). Why: MANIFEST §8 says hooks never see standard `tb.*` ops, but today's bridge (`hookMatches` in `calls.ts`) does not check `op.standard`, so it still sends them (the packages lead is fixing the bridge). Without it, Closed would refuse an agent's `tb_hold_status` and Inbox's `tb.holds_pending` (the operator Inbox would go blind), and Verification would hold the hold checks themselves.

Calls that are NOT exempt and need an owner allow rule in Verification or Closed (reported, not built in): Governance → `connect.identities_list` (directory handles), Evolution → kanban, Creative/Observer → `inbox.inbox_ask`, Live artifacts/Observer → knowledge and kanban reads. Rules' catalog read is HTTPS outside the bridge and is not gated.

## Scopes, hooks and companions

- **Scopes:** None. `needsAgentDirectory: true`. Pending English drafts feed `pendingHolds` (TBD badge).
- **Hooks:** Three, all products. `rules_gate`: phase `before`, order 0, timeout 1000 ms (own budget 250 ms). It reads only local cached tables: no app call, no model, no network. Any error or overrun refuses. A hold needs bridge 0.1.17 or later, else it degrades to a refusal. `rules_context`: phase `context`, emits `rules.narrowing` (v 1, or v 2 when `deepDatasets` is present) with `memoryTags` and `deepDatasets` (consumed by Knowledge), `rules.matched`, `rules.onBehalfOf`. `rules_filter`: phase `after`, read effects only, 2000 ms, redacts result objects whose `tags[]` fail the narrowing.
- **Companion grants it asks for:** `fleet.directory_feed` (read; Governance, contract `fleet.directory_feed/1`). The copy (teams, contact trust) is refreshed at start, every 60 s, on agent-list changes, and from owner pages if older than 60 s. A refusal or an invalid answer clears it at once; a transient failure keeps it up to 10 minutes. **Fail closed:** when the copy is unavailable, deny and hold rules that name Fleet facts apply and allow rules that name them do not (C230, C236). Mapping: keys `agent:<id>`, `contact:<id>`, `handle:<canonical>`, each with its HOLDERS (a handle can have several). Deny/hold rules match when ANY holder matches (membership, trust); allow rules need EVERY holder active (not blocked, departed, removed) and matching; trust is the holders' raw trust set, unknown = `unreviewed`. Without the facts the highest severity among the closed deny/hold rules before the first fact-free match decides. A skipped allow rule's narrowing still applies, and the after hook redacts by the verdict the before hook pinned.

## Data

- **Stored:** Migrations 0001 to 0008 (0003 to 0005: `fleet_trust`, `fleet_sync.usable`, `fleet_members.active`, `drafts.source`; they clear the 0.2.x Fleet copy; 0006: nullable `decisions.caller_product`; 0007: `rule_revisions.from_rev`, additive, NULL on older rows; 0008: `settings` and `mode_changes`, the default mode, see below): `rules` (current spec JSON, priority, active, soft delete), `rule_revisions` (append-only: created, updated, deleted, restored), `drafts`, `decisions` (trace per call and phase; pruned to 30 days and 100,000 rows), `fleet_teams`, `fleet_members`, `fleet_trust`, `fleet_sync`, `catalog_manifests`, `catalog_sync`, `settings` (row `default_mode`), `mode_changes` (append-only: at, actor, from, to).
- **Never stored:** Call inputs and outputs. Traces hold ids, product, op, effect, decision, reason, rule reference and onBehalfOf.

## External calls and background work

- **External:** The only outbound call is the app catalog (`src/catalog.ts`): the signed release index from the platform `registry` release, JWS-verified with a pinned Ed25519 release key, then each manifest URL checked against `manifestDigest` and `validateManifest`. Refresh at start and every 6 hours (every 60 s after a failure), 15 s timeout, 4 MB cap, never inside a hook. It is used only by writers. Without a catalog, a rule that names apps is refused (`catalog_unavailable`, 503); stored rules are never deleted. **The release key is copied into this app; a release-key rotation needs a new Rules release.**
- **Owner's model (optional, C373 Q-A):** `rule_compose` may call the owner's bound `utility`/`reasoning` model to help draft (see the English box); never in a hook, never to decide.
- **Background:** Fleet refresh (60 s) and catalog refresh (6 hours); decision pruning.
