# Rules & Approvals (Tealbrick mini app): architecture

State: verified against the repo on 2026-10-17. Claims cite paths in this repo. Anything not verified is marked UNVERIFIED. For the whole system see the system `ARCHITECTURE.md` and `SYSTEM-OVERVIEW.md`.

## Common app pattern (verified for this repo on 2026-10-17)

- **Runtime**: Node 24, TypeScript run through `tsc` to `dist/`, UI built by `scripts/build-ui.ts` (no bundler; content-hashed `assets-<hash>/`). The app is started by `startApp` from `@opt2-tealbrick/miniapp-sdk` (`src/main.ts`).
- **Dockerfile**: two stages on `node:24-slim` pinned by digest, `pnpm install --frozen-lockfile --ignore-scripts`, `pnpm run build && pnpm prune --prod`, the manifest also copied to `/opt/tb/tealbrick.manifest.json` (the `tb-exec` default), `USER node`, no `VOLUME`. The SDK drops root to uid 1000 itself when the platform starts the container as root (Railway volumes are root-owned).
- **Data**: one SQLite file `TB_DATA_DIR/app.db` owned by the SDK. App tables use their own prefix; SDK tables use `tb_*`. On Railway there is ONE volume per service: the backup directory is `<data mount>/backup`, so the volume size is data plus backup (C28).
- **Migrations**: `migrations/NNNN_name.sql` (or `.ts` exporting `up(db)`). The SDK enforces forward-only: gap-free from 0001, one transaction each, sha256 recorded in `tb_migrations`. A changed, missing, misnamed or `down` migration stops the app with `migration_invalid`.
- **Backups and restore**: SDK cron runner writes `tb-backup-<UTC>.tar.gz`; export `tealbrick.export/1` never carries the instance key, KEK, keys, secrets or sessions. Restore at next boot with `TB_RESTORE_FROM`.
- **Authorization**: the bridge gates (`gate()`); the SDK decides (`authorize()`): run, hold or refuse. Holds and receipts live in the app's own `tb_receipts` table. Raw call input is never stored, only a digest.
- **Manifest** `tealbrick.manifest.json` is the only source for operations, scopes, settings, hooks, companions, skills, runtime hints, backups and UI paths. Schema `tealbrick.miniapp/2`, `sdkMajor 1`, `source.license Apache-2.0`. Agent ops become MCP tools `<product>__<op>`. Person ops are owner UI only.
- **Generated**: `gen/` (openapi, kit, docs, railway) is produced by `tb-gen` and is not committed. The typed client kit is built into `dist/kit` and imported as `#kit` in apps that have one.
- **Standard UI pages** (from the kit `AppShell`): Holds, Receipts, Agents and scopes, Keys (where the app has keys), Backups and export.
- **Licence files**: `LICENSE` (Apache-2.0), `NOTICE`, `THIRD_PARTY_NOTICES.md`. The brand mark and app art are Tealbrick artwork and are not Apache-licensed.
- **Private by design**: no public address. Only the bridge is public.

## Rules & Approvals: what it does

Rules declares hooks on all products. **If Rules is down, every agent call in the workspace is refused (`hook_failed`), reads included.** A hook leaves the gate only by explicit owner action, never by a transient state (C117, L33).

Rule shape: `title`, `active`, `priority` 0 to 1000 (lower first), `match` {agents, modes, products, operations, `tools`, effects, `callerTeams`, `callerTrust`, `callerProducts`, `callerWorkflows`, `recipients` {teams, trust, known}, `onBehalfOf` {teams, ids, kinds, trust}}, `outcome` {decision allow, deny or hold; reason up to 280 characters}, optional `narrowing` {`memoryTags` {anyOf, noneOf}, `deepDatasets` {anyOf, noneOf}}. The first matching active rule decides. No match: the workspace default mode decides (section "Default mode"). Outward, destructive and money calls are always recorded. An unverified `onBehalfOf` claim may only make a decision stricter (C82).

## Operations (from `tealbrick.manifest.json`)

20 operations. No hold families on its own ops (Rules produces holds on other apps with family `policy`).
- Agent (an app with a companion grant may call them too): `rules_explain` (read), `rule_draft_submit` (write; draft only; records who proposed it: `source` {kind `agent` or `app`, product, name}), `draft_status` (read; answers only for drafts the caller itself submitted, any other id is `not_found`, the same as a missing one), `floor_status` (read; `listing: workflow`; verified product `fleet` only).
- Person read: `rules_list`, `rules_get`, `rules_preview` (dry run), `rules_preview_recent` (D11: an unsaved rule over the last recorded gate decisions, `src/recent.ts`; only the facts the decision log keeps; nothing stored), `decisions_list`, `drafts_list`, `fleet_status`, `rule_compose` (C373 J3: the owner's English → proposed rules, no state), `mode_get` (C373c: the default mode, its history and the system lines), `floor_list` (C380). Person write: `floor_clear` (C380), `rules_set`, `rules_delete`, `rule_compose_save` (C373 J3: the proposal as a pending draft, `source.kind` `owner`, idempotency required; it applies only through `draft_decide`), `rule_restore` (C373 Q-7: an earlier revision becomes current as a new `restored` revision; a deleted rule comes back; same writer checks as `rules_set`), `draft_decide`, `mode_set` (C373c: the default mode; looser needs `confirm: true`). `rules_list` rows carry `deleted`; `rules_get` revisions carry `change` `restored` with `from`.
- English box (C373, J3): `src/compose.ts` is a pure, deterministic parser (no model, no network) behind a `Drafter` seam (`rule_compose.drafter`: `parser` or `model`). The optional model drafter (`src/model-drafter.ts`) runs only when the parser left words unread, the bridge declares cap `model_roles` and SDK `modelRole("utility")` (else `"reasoning"`) resolves; it calls the owner's bound provider (OpenAI-compatible chat completions or the Anthropic messages API, 20 s timeout), parses the JSON answer and vets it like the parser's (plus `namesProblem`: only ids the directory lists); it is used only when it keeps at least as many rules, and any failure falls back to the parser with a note. The key is never logged or returned. Hooks never reach it. Names come from the agent directory (`events.agentsChanged`, kept in memory by `src/directory.ts`), the Fleet copy (team names) and the catalog (product ids plus a few display names). A name that is not found or that two agents or teams share is never guessed (the sentence is listed as not read, with close names). `vetProposal` runs the writer checks (manifest RuleSpec schema, then `ruleProblem`) on every drafter's rules; the parser drops a whole sentence when one of its rules is refused, and never proposes an allow rule from a partial reading. Placement (S2, safety; any drafter): composed refuse/hold rules run before every existing active allow (at most priority 10), composed allow rules after every existing active refuse/hold (their highest priority + 10, at least 20); with a refuse/hold at 1000 an allow is not proposed. Each proposal line says the priority and why. Agent names: the `agentsChanged` list plus the names the owner page read from `tb.agents_list` (`rule_compose.agents`), so names resolve right after a restart; no table (a migration 0009 would break the gap-free rule while 0008 is unmerged). The optional model roles do not change readiness: SDK 0.1.40 reports only required roles (test in `test/model-drafter.test.ts`). "Evolution's outward actions" / "calls from the Evolution app" name the app that makes the call (`callerProducts`).
- Writers refuse a rule that can never match (unknown app or op, person-only op, impossible effect, `tools` on a static op or on an app without a dynamic op) using the app catalog. An empty `anyOf` from an owner is refused (C115), for `memoryTags` and for `deepDatasets`. Writers also refuse an invalid or repeated `callerProducts` id and a combination of `callerProducts` with `modes`, `callerTeams` or `agents` that lists only `agt_` ids (an app call has none of them).
- Spec 0.1.68 (C336 RQ-2, with C325 and C330; specs#47): `match.tools` matches the bridge's `target.tool` (case-sensitive; an entry `x` matches `x` and its resolved variants `x__…` only, QA-RULES18-4; an entry containing `__` is refused at save; no other wildcard). Without `target.tool`: a static op never matches; a dynamic op (placed by the cached app catalog, `dynamic` fact; an op the catalog cannot place counts as dynamic) fails closed: deny and hold rules apply, allow rules do not, and `detail.toolUnknown` is recorded; `narrowing.deepDatasets` limits the datasets a data app may read. Both are fields of the rule JSON in the `rules.spec` column, so there is no migration: a stored rule without them reads as before. Rules only emits `deepDatasets` in `rules.narrowing`, with `v: 2` exactly when it is present (else `v: 1`); it never reads or filters dataset rows, and the after hook still redacts by memory tags only (a dataset narrowing is applied by the data app before it reads, SDK-API 18.5). The decision log keeps the tool name in `detail.tool` and shows it as `target.tool`.
- Dataset ids compare EXACTLY (case-sensitive, no trim). The comparison (`datasetsMatch`, SDK-API 18.5 rules 3 and 4: key absent passes; key present needs a non-empty id list, under `noneOf` as under `anyOf`; then `anyOf` needs every id in it and `noneOf` excludes; no lineage, rule 4a: derived datasets are listed explicitly) is a LOCAL copy in `src/engine.ts` with a TODO: no released @opt2-tealbrick/manifest carries the shared helper yet (0.1.31, pinned, is spec 0.1.64), and the copy is deleted when Rules pins the release that does (one mechanism, L1). The pins and the SDK types carry spec 0.1.64 shapes, so `target.tool` is read structurally (`toolOf` in `src/hooks.ts`, marked `spec 0.1.68`). The editor does not show "needs a bridge with `hook_tool`" (Core and the GUI do); SDK 0.1.37 and later give the app `ctx.bridgeCaps`, which a later release can use for that hint.
- Caller identity (S4-5): an app caller is its VERIFIED product (hook `caller.product`, bridge 0.2.2 or later; `ctx.caller.product` on ops), never a name; an agent is its agent id and never matches `callerProducts`. An app with no valid product fails closed with the same machinery as unavailable Fleet facts (`closedOnProduct`, trace detail `callerProductUnavailable`). `rules_explain` reads an app's decisions by `decisions.caller_product`, older rows by instance id. Product is identity (C237, accepted): two live instances of the same verified product share one `rules_explain` history; products, agents and unverified apps (by instance id) stay isolated from each other. Writers check `callerProducts` against the signed app catalog exactly like `products` (`catalogProblem`; no catalog = `CATALOG_MISSING`, `catalog_unavailable` 503), and `ensureCatalog` reads the catalog for it too.
- C373 match fields (0.5.0): `callerTrust` (calling agent's trust, a Fleet fact), `recipients` (who an outward call goes to: handles → holders → teams, trust, known; unknown fails closed with `recipientsUnknown`; effects exactly `["outward"]`), `callerWorkflows` (verified workflow of an `evolution` app caller; without the cap `app_workflow_grants` a call without a workflow fails closed with `closedOnWorkflow`). All three use the closed/skipped machinery of `judge`/`firstMatch` in `src/engine.ts` (flags `onRecipients`, `onWorkflow`). `recipientsOf`, `workflowOf`, `registerBridgeCaps` live in `src/hooks.ts`. CallFacts hold per-recipient Fleet facts only, never a handle; traces keep the recipient count.
- Default mode and missing facts: `verdictOf` lets the default mode decide over a closed rule when the scan ended on closed rules only and the mode is stricter (Hit `exhausted`), so a missing fact never makes a call looser than the no-match path with known facts. Fuzz: `test/c373-fail-closed-fuzz.test.ts`.

## The company floor (C380, since 0.7.0)

One line before every rule, in all modes, that the owner does not edit (overrides C84, DEV default on). `rules_gate` calls `floorSubjectsOf` and `floorHit` (`src/hooks.ts`, `src/engine.ts`): caller agent, acting agents, claimed requester (under its key, and as a handle when its id reads as one), every well-formed recipient (also from a list the rules call unknown). The bridge sends no `target.recipients` yet, so `connectInputRecipients` reads Connect's send ops from the call's own input (A29); recipient rules still read only the bridge's list and stay fail closed. Answer: `FLOOR_REASON` for all of them, one sentence, so the words do not say who is not active (S2-8); Decisions keeps the full reason and no handle; `rules_explain` returns the sentence. `evaluate` does not read the floor, so the context and after phases keep their narrowing.

Data (`src/floor.ts`, migration 0010): `floor_entries` is apart from the Fleet read model on purpose (S1-1). That copy is cleared by a refusal and given up after 10 minutes; the floor is not. `writeFloor` runs only inside the last transaction of a full valid read (`writeSteps`, `src/store.ts`). A refusal, an invalid answer, an expiry, a crash or `unchanged` never touches it. A read with no lifecycle facts (no row carries `floor`: a Governance that ignores `accept`, a rollback, the fallback read, an empty directory) cannot lift a lifecycle stop and does not move `floor_state.feed_revision`; it decides only what it can see, trust `blocked` and a departed contact. After a Governance rollback the lifecycle stops stay until the owner's `floor_clear`. **Going back (N2-2):** `floor_state` keeps the highest revision read and the feed's `epoch`. A full read below that revision, or an aware read with another epoch (Governance changes it on a restore; a fresh install has another), marks the floor regressed: reads only add, nothing is lifted, `floor_entries.listed = 0` marks what Governance's list no longer has, and the Rules page and `floor_status` say so. Clear all ends it. Without an `epoch` from Governance only a lower revision is seen, which misses a restore whose later bumps pass the old high. The gate reads `floorIndex` without `fleetFacts().available`; a table that cannot be read refuses (FAIL_CLOSED). A row with no `floor` inside an answer that has it is blind on its own. A row stops when `floor: true`, trust `blocked` or a stopping lifecycle says so; no field lifts another; a lifecycle stop names the entry before `blocked`, so a blind read that sees the block lifted keeps it. A feed with no `floor` key (Governance 0.3.x): trust `blocked` or a departed contact. Stricter than ACCESS.md on purpose: a rollback of Governance must not reopen a blocked agent.

Limit: a full valid read is authority. A compromised Governance can reopen a stop by saying `active` per entry, and can stop anyone; the way out is the owner's `floor_clear` and removing Governance (a refused read cannot add or lift). `floor_clear` forgets `feed_revision` and forces the next read to be a full one: an entry Governance still lists comes back at that read. Exempt from the floor: Rules' own `rules_explain`, `draft_status`, `floor_status`, by product and op, and Rules' own feed read. `rule_draft_submit` is not exempt.

## Caller roles (C380 T2-a, since 0.7.0)

- `match.callerRoles` names the flat roles of Governance (feed `roles`, read with `accept: ["agent_handles", "lifecycle", "roles"]`) of the CALLING agent. It has the semantics of `callerTeams` and nothing more: deny and hold rules see every holder (also a blocked, departed or removed one), allow rules only holders that count; an app caller never matches (`caller is not an agent`); a call with no acting agent is the app's own work and matches no role rule.
- **Acting agents narrow only.** A deny or hold rule by role also matches an app call that acts for an agent that has the role (any one of them); an allow rule never reads the acting agents (`ActingFact.rolesAny`).
- **Fail closed.** Fleet facts unavailable: a deny or hold by role applies, an allow does not (its narrowing stays). A copy read WITHOUT roles (a Governance that does not know them, the fallback read after a 400 to `accept`, a restart or update before the first full read) is read the same way (`rolesKnown` false): nobody is known to hold a role, so no rule by role may be taken as "does not apply". A role that ended or is archived is not in the feed, so a rule that names it matches no one: for a deny that is the owner's intent, and the editor keeps the unlisted id visible so it can be removed.
- Tables `fleet_roles`, `fleet_role_members` (migration 0011), kept apart from the teams so a team id never matches a role. `parseFeed` checks `roles` by hand (the frozen schema allows extra members): at most 200 roles, 4000 members each, unique ids and members, kinds `agent` or `contact`; a bad list refuses the whole answer. `fleet_status` lists the roles for the editor; `rules_preview` answers `callerRoles`.
- A role is a record. With no rule that names it, it decides nothing. The decision log does not keep roles, so a rule by role cannot be checked against past calls.

## Acting agents (C378, since 0.6.0)

The bridge writes `tb.acting` on an app call that acts for an agent (spec 0.1.88, BRIDGE §8.7): inside that agent's own open call, or later by a ticket the bridge signed during that call. `src/hooks.ts` `actingIdsOf` reads it strictly (malformed: the gate refuses) and `actingFacts` adds the Fleet facts.
- **Narrow only.** Deny and hold rules naming `agents`, `callerTeams` or `callerTrust` also match when ANY acting agent matches. Allow rules never read acting agents, because the calling app decides which of its calls carry them. Allow for app work: `callerProducts`, `callerWorkflows`.
- **No acting agent** = the app's own work (owner schedule, timers, plumbing): agent rules do not match it, product and workflow rules and the mode decide.
- Decisions names the agents (`detail.acting`) and marks a send-time check (`detail.atSendTime`, bridge `tb.recheck`). `rules_preview_recent` does not replay acting agents: the old rows have none.

## Default mode (C373c, since 0.5.0)

Martin's decision C373c: one workspace-wide mode for calls that match NO rule. `permissive` = allow (every release before 0.5.0 behaved so; a fresh install and an updated 0.3.2/0.4.x install start here, migration 0008), `verification` = hold, `closed` = refuse.

- **Where it acts:** only the no-match path of `evaluate` (`src/engine.ts` calls `modeVerdict` in `src/mode.ts`). A call that matches a rule is decided by that rule in every mode: an allow rule still allows with its narrowing, deny and hold rules decide as before. The fail-closed machinery for Fleet facts, products and tools is unchanged; an allow rule skipped for an unavailable fact leaves the call unmatched, so in Verification or Closed the mode holds or refuses it (stricter, never wider). An unverified on-behalf-of claim is evaluated with and without the claim rules as before (C82), both with the mode, so a claim cannot open a Closed workspace.
- **Answers:** Verification answers a normal Rules hold (family `policy`, "Needs owner review: no rule covers this call (Verification mode)"): the TARGET app holds the call and it shows in that app's Holds and in the operator Inbox (`tb.holds_pending`); the approved retry runs once, like any Rules hold. Closed refuses "Rules: no rule allows this call (Closed mode)". Without the hold verdict (old bridge) a Verification hold refuses (fail closed). Agents, app (companion) callers and Evolution engine calls all reach `rules_gate`, so the mode applies to all of them.
- **Speed:** the mode lives in a per-database cache (`src/mode-store.ts`) next to the rules cache; the gate does no extra query per call; `mode_set` refreshes it. A missing or damaged row reads as `closed` (fail closed; the migration inserts the row and a CHECK keeps the value valid).
- **Context and after hooks** evaluate without the mode (Permissive): a call reaches them only when the gate allowed it or the owner approved its hold, and it must carry the narrowing it would carry in Permissive mode, including that of skipped allow rules.
- **Changing it:** person op `mode_set {mode, confirm?}` (idempotency required). Looser (closed → verification → permissive) needs `confirm: true`, else 409 `confirm_required`; tighter needs none; the same mode again changes and records nothing (a replay is harmless). Every change is a `mode_changes` row (who, when, from → to); `mode_get` returns the mode and its history; `rules_list` returns the mode and the system lines. Agents cannot change it (person op).
- **Explaining it:** a mode hold or refusal is a decision trace with detail `{decidedBy: "mode", mode}` (an exemption that let a gated-effect call pass: `{decidedBy: "exemption", mode, exemption}`). Every call that is not a read and matched no rule is recorded, also in Permissive mode, with `{decidedBy: "mode", mode}` (QA-C373-RU-2; reads that match no rule are not recorded); a row from before 0.5.0 dev.5 with no rule and no `decidedBy` reads as Permissive (`traceDecidedBy`). `rules_explain` returns `decidedBy` (`rule`, `mode`, `exemption`) and `mode`; the Decisions page says "decided by … mode"; `rules_preview` returns the mode outcome (`modeNote`) and takes a `mode` to compare. When `rule_compose` (the English box) proposes an allow rule, its first note says what the mode does outside it (`composeModeNotes`).

### Built-in exemptions (the mode never holds or refuses these)

They act ONLY on the no-match path: an owner rule that matches such a call still decides it (an owner may deliberately refuse Rules' own feed read). Each is shown on the Rules page as a read-only "system" line (`EXEMPTIONS` in `src/mode.ts`).

1. **`rules-governance-feed` (required by C373c (a)):** caller type `app` with the VERIFIED product `rules` (the bridge's signed `caller.product`), target product `fleet`, op `directory_feed`. Why: Rules reads Governance through the companion grant, and the bridge runs every before hook on companion calls, Rules' own included (bridge `calls.ts` `hookMatches` has no self-exemption). Without it, Closed would refuse the feed read (the refusal clears the Fleet copy, so every team rule turns strict for good) and Verification would park it as a hold in Governance: a fail-closed loop that only the owner could break. Not exempt (tests fire on each): an app caller without a verified product (`ins_` id only, or a value that is no product id), another fleet op, another caller product, an agent, and Rules calling any other app.
2. **`inbox-owner-alerts` (the hold-notification loop):** caller type `app` with the VERIFIED product `inbox`, target product `connect`, ops `buzz_dm`, `buzz_dm_first`, `channel_dm`, `channel_dm_first` only (the ops Operator Inbox uses to DM the owner, opt2-tealbrick-inbox `src/alerts.ts`; its manifest companion lists exactly these four). Why: in Verification a mode hold reaches the owner's Inbox, and Inbox DMs the owner through Connect; that DM matches no rule, so the mode would hold it too: a new hold, another DM, another hold, without end, and the owner never gets the first alert. Closed would refuse every owner alert. Not exempt (tests fire on each): an app caller without a verified product, another product calling `buzz_dm`, Inbox calling another Connect op, an agent calling `buzz_dm`, the same op name on another app. An owner rule on Connect still decides these calls. The exemption is outward, so its calls are recorded with detail `{decidedBy: "exemption", exemption: "inbox-owner-alerts"}`.
3. **`rules-self-service`:** target product `rules`, ops `rules_explain`, `rule_draft_submit`, `draft_status` (any caller). Why: in Closed or Verification an agent must still be able to ask why it was stopped and to propose a rule; a draft changes nothing until the owner approves it (C84), and the two reads return only the caller's own rows. Without it, Closed cuts agents off from the only way to ask for a rule, and Verification would hold a draft that then needs a second approval.
4. **`platform-standard-ops`:** any target op in the reserved `tb.` namespace (manifest op ids can never contain a dot, so no app op can look like one). Why: MANIFEST §8 says hooks never see standard `tb.*` ops, but today's bridge (`hookMatches` in `calls.ts`) does not check `op.standard`, so it still sends them (the packages lead is fixing the bridge). Without it, Closed would refuse an agent's `tb_hold_status` and Inbox's `tb.holds_pending` (the operator Inbox would go blind), and Verification would hold the hold checks themselves.

5. **`knowledge-governance-feed` (C378):** verified `knowledge` → `fleet.directory_feed`. Same read-only feed; Governance's FEED_READERS admits only Rules and Knowledge. Without it a Closed workspace leaves Knowledge on an old copy, and its 60 s timer would ask the owner every minute in Verification.
6. **`governance-reads-connect` (C378):** verified `fleet` → `connect.identities_list`, `contacts_list`. Read-only names and handles; recipient rules need them, else they fail closed for ever (QA VERDICTS: Closed denied it).
7. **`owner-decision-relay` (C378):** verified `connect` → `inbox.item_decide_dm`. It carries the owner's own Approve or Deny; Inbox accepts it from Connect only and checks the person. A hold on it would need another answer (a loop). No new authority.
8. **`apps-ask-owner` (C378):** any app with a verified product → `inbox.inbox_ask`, `inbox_status`, `inbox_reply`, `inbox_withdraw`. They reach only the owner and an app sees only its own items; a workflow `approval` step needs them, and a poll of `inbox_status` would make a hold per tick. Agents are not covered.
9. **`apps-read-setup` (C383, audit hole 7):** caller type `app`, VERIFIED product `observer` to Connect `data_accounts_list`, `data_catalog`, Knowledge `areas_list`; VERIFIED product `evolution` to Connect `tool_shares_mine`. Why: names, shapes and counts of what the owner shared, asked each time the app's own page opens; in Verification each ask is one more hold. Never for a call with `tb.acting` or `evolution.*` context (`forWork`). `data_pull` stays under the mode.
10. **`evolution-scans-task-board` (C383, audit hole 7):** caller type `app`, VERIFIED product `evolution`, target `kanban.issues_list`, not `forWork`, input exactly `{status: "done", limit: 200}` (`detectorScan`). Why: the detector's 15 min timer was the last timer that made one new hold per tick in Verification (VERDICTS C378). This reads issue text of finished issues in the projects Evolution can read, shared projects included; the system line says so, and a rule can refuse it. A workflow step carries `evolution.workflow` and stays under the mode. A poll trigger carries no context, so only a poll with this same input is covered.

Rule for a new exemption: internal traffic only, a verified product (or no effect beyond the owner's own review), exact ops, no new authority, and a test that fires on every near miss. Calls that are NOT exempt on purpose, because they are the work apps do for the owner: Observer and Evolving Workflows reading and writing other apps (Connect, Knowledge, Task Board), Live artifacts' refresh. They need an owner allow rule or an Access page row in Verification or Closed.

## Scopes, hooks and companions

- **Scopes:** None. `needsAgentDirectory: true`. Pending English drafts feed `pendingHolds` (TBD badge).
- **Hooks:** Three, all products. `rules_gate`: phase `before`, order 0, timeout 1000 ms (own budget 250 ms). It reads only local cached tables: no app call, no model, no network. Any error or overrun refuses. A hold needs bridge 0.1.17 or later, else it degrades to a refusal. `rules_context`: phase `context`, emits `rules.narrowing` (v 1, or v 2 when `deepDatasets` is present) with `memoryTags` and `deepDatasets` (consumed by Knowledge), `rules.matched`, `rules.onBehalfOf`. `rules_filter`: phase `after`, read effects only, 2000 ms, redacts result objects whose `tags[]` fail the narrowing.
- **Companion grants it asks for:** `fleet.directory_feed` (read; Governance, contract `fleet.directory_feed/1`). The copy (teams, contact trust) is refreshed at start, every 60 s, on agent-list changes, and from owner pages if older than 60 s. A refusal or an invalid answer clears it at once; a transient failure keeps it up to 10 minutes. **Fail closed:** when the copy is unavailable, deny and hold rules that name Fleet facts apply and allow rules that name them do not (C230, C236). Mapping: keys `agent:<id>`, `contact:<id>`, `handle:<canonical>`, each with its HOLDERS (a handle can have several; contacts by their handles and, since 0.5.0, agents by `agents[].handles`, which Rules asks for with `accept: ["agent_handles"]`; the runtime schema is Governance's derived `fleet.directory_feed.1.agent_handles.schema.json`, a superset of the spec copy). Deny/hold rules match when ANY holder matches (membership, trust); allow rules need EVERY holder active (not blocked, departed, removed) and matching; trust is the holders' raw trust set, unknown = `unreviewed`. Without the facts the highest severity among the closed deny/hold rules before the first fact-free match decides. A skipped allow rule's narrowing still applies, and the after hook redacts by the verdict the before hook pinned.

## External calls and background work

- **External:** The only outbound call is the app catalog (`src/catalog.ts`): the signed release index from the platform `registry` release, JWS-verified with a pinned Ed25519 release key, then each manifest URL checked against `manifestDigest` and `validateManifest`. Refresh at start and every 6 hours (every 60 s after a failure), 15 s timeout, 4 MB cap, never inside a hook. It is used only by writers. A single manifest that cannot be read is skipped on its own and listed (`catalog_sync.skipped`, `rules_list.catalog.skipped`); `catalog.error` is a failed read of the index. A failed fetch of the index or its signature is read again (3 tries). Without a catalog, a rule that names apps is refused (`catalog_unavailable`, 503); stored rules are never deleted. **The release key is copied into this app; a release-key rotation needs a new Rules release.**
- **Owner's model (optional, C373 Q-A):** `rule_compose` may call the owner's bound `utility`/`reasoning` model to help draft (see the English box); never in a hook, never to decide.
- **Background:** Fleet refresh (60 s) and catalog refresh (6 hours); decision pruning.

## Safety notes from the 0.5.0 review (C373)

- Caller teams are agent facts: an app caller never matches a `callerTeams` rule. Rules' own `fleet/directory_feed` read (exemption `rules-governance-feed`) is never refused or held by a rule that applies to it only because the Governance facts are missing; only a rule that names it (`products: ["fleet"]`, `callerProducts: ["rules"]`) can stop it, and the UI warns on such a rule.
- The Fleet copy knows whether it was read WITH agent handles (`FleetFacts.agentHandles`, in memory; false after a restart until the first full read). Without them every recipient is unknown (fail closed for recipient rules).
- Placement: the English box places deny before hold before allow relative to the existing rules (active and inactive). Approval (`draft_decide`) places a draft again against the current rules (`src/placement.ts`); "Allow always" (`src/ui/hold-allow.ts`) goes after every refuse rule that could match, active or not, and before the hold that held the call.
- The parser never turns a negation into an allow (exact refusal or `unmatched`); the model drafter only adds rules and gets directory names as quoted JSON data.
- Dependency (S4-6): `bridgeCaps` is advisory. When the bridge advertises `app_workflow_grants`, Rules reads a call without `caller.workflow` as "not a workflow call"; that is safe only if such a bridge always forwards `workflow`.

## Is the hook on? (C383, D13)

Portal holds the owner's per-hook switch and the bridge skips a switched-off hook, so Rules gets no signal. `src/hook-watch.ts` uses Rules' own `directory_feed` read as a probe: the bridge sends it through the hooks, so when the read comes back `ok` and a hook of Rules did not run during it, that hook is off. A refusal, a hold or no Governance says nothing (`unknown`, never `on`), and an answer older than 5 minutes is `unknown`. Memory only. The page reads op `hook_state` and shows a warning that cannot be dismissed on every page. Portal shows the same from its own hook list. Limit: in a workspace with no Governance, Rules' page can say only that it cannot tell.
