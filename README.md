# Rules & Approvals (Tealbrick mini app)

Rules & Approvals (product id `rules`): the per-workspace policy. It gates other apps' calls with allow, refuse or hold, always with a recorded reason. English rules are proposals: the owner types one in Rules (a deterministic reader, no model) or asks their own agent, and approves the draft; Rules never calls a model to decide. Built on the Miniapp SDK.

**Status:** 0.7.0, on the dev channel until promoted. Before it: stable and qa1 0.3.2; `main` is 0.5.0 (dev channel until promoted; 0.4.x was never released; 0.3.0 is never promoted, C266; it needs Governance 0.2.0 or newer for team rules, else they fail closed). Visibility: public, Apache-2.0. Published as the public GHCR image `ghcr.io/tealbrick/opt2-tealbrick-rules` (on 2026-10-17 its version tags are the plain build `0.2.12`, its earlier dev pre-release, and a `sha-` tag; there is no `0.2.11` tag in that registry). The manifest declares `requires.bridge: 0.2.11` (holds need 0.1.17; the optional model roles in `settings` need 0.2.11).

## No secrets policy

This repository is public. It must never contain secrets or personal data, and neither may its issues or pull requests:

- No API keys, tokens, passwords, private keys, deployment secrets, `.env` files or connection strings. Use `.env.example` with placeholder values only.
- Runtime secrets live in the deployment platform (Railway variables) and are copied between services without printing them.
- No personal names, private agent configurations or customer data.
- Every pull request and every push to `main` runs a secret scan (gitleaks, the `secret-scan` step in `.woodpecker/ci.yaml`). GitHub secret scanning and push protection are not enabled on this repository, so this CI step is the guard. Optional local guard: `pre-commit install` (`.pre-commit-config.yaml` runs gitleaks).
- If a secret is committed anyway: rotate it first, then remove it from history.

## App

`tealbrick.manifest.json` is the only description of the app. The SDK derives the routes, input and output validation, OpenAPI, receipts, holds, idempotency, scopes, backups and status from it. You write handlers by operation id (`src/app.ts`) and plain migrations (`migrations/`). The app has no keys. The only app-specific environment variable is the test-only `TB_RULES_CATALOG_OFF`.

## What Rules does

Rules declares hooks on all products. **If Rules is down, every agent call in the workspace is refused (`hook_failed`), reads included.** A hook leaves the gate only by explicit owner action, never by a transient state.

Rule shape: `title`, `active`, `priority` 0 to 1000 (lower first), `match` {agents, modes, products, operations, `tools`, effects, `callerTeams`, `callerTrust`, `callerProducts`, `callerWorkflows`, `recipients` {teams, trust, known}, `onBehalfOf` {teams, ids, kinds, trust}}, `outcome` {decision allow, deny or hold; reason up to 280 characters}, optional `narrowing` {`memoryTags` {anyOf, noneOf}, `deepDatasets` {anyOf, noneOf}}. The first matching active rule decides. No match: the workspace **default mode** decides (below). An empty `anyOf` from an owner is refused.

`match.tools` (spec 0.1.68, bridge cap `hook_tool`) lists tool names (the bridge's canonical names, `^[a-z][a-z0-9_]{1,47}$`, up to 100, needs `products`): it matches a call whose hook `target.tool` (the dynamic entry name of a dynamic call) is in the list, by exact, case-sensitive equality, plus the resolved variants of a listed tool: an entry `x` also matches `target.tool` starting with `x__` (Connect resolves `gmail_send` to `gmail_send__first_contact`, which runs the same upstream tool; QA-RULES18-4). Catalog names never contain `__` (an entry that does is refused at save), so this is no general prefix wildcard: `gmail_sendx` and `gmail_send_bulk` do not match `gmail_send`. Allow, deny and hold rules follow the same rule. A call WITHOUT `target.tool`: on a static op a rule with `tools` never matches; on a dynamic op (or one the app catalog cannot place) it fails closed like the Fleet facts do (C236): a deny or hold rule with `tools` APPLIES, an allow rule with `tools` does not. So an older bridge or a bridge bug cannot switch a refusing tool rule off. The decision detail records `toolUnknown: true`. `narrowing.deepDatasets` (spec 0.1.68; each list holds up to 64 ids of 1 to 128 characters, and the object needs `anyOf` or `noneOf`) limits the datasets a data app (Knowledge deep knowledge) may read for the call. Ids are the data app's canonical dataset ids: EXACT and CASE-SENSITIVE, never trimmed or case-folded (a name with a space at either end is refused at save). It merges across matching rules per key: `anyOf` lists intersect (disjoint gives `[]` = nothing passes), `noneOf` lists unite, and a list present on either side survives (absent is not "all"). Rules only emits it; the data app applies it before it reads. Rules does not follow lineage: a view or pipeline output built from a disallowed dataset is a dataset of its own, so owners list derived datasets explicitly (SDK-API 18.5 rule 4a). Rules cannot read the bridge capabilities with the pinned SDK, so it does not show "needs a bridge with `hook_tool`" on rules with `tools` (Core and the GUI do, BRIDGE v0.1.68).

- **Gate (`rules_gate`, before hook, every product):** the first active rule that matches the call decides (lower priority first): allow, refuse or hold, always with the rule's reason. It answers from local cached tables only (no app call, no model call, no network), with its own budget of 250 ms (hook limit 1 s); any error or overrun refuses (fail closed). Outward, destructive and money calls, and every call a rule decided, are recorded as decision traces keyed by the bridge `callId` (join with the target app's receipts). Traces hold ids, product, operation, effect, decision, reason, rule reference and `onBehalfOf`, never call inputs or outputs; they are pruned to 30 days and 100,000 rows.
- **Hold:** a hold rule answers `{allow: false, hold: {family: "policy", reason}}`; the bridge carries the verdict in the call proof and the TARGET app holds the call in its own holds table (`heldBy` = `rules/rules_gate`). The owner decides there; the retry of the same input runs once; a refusal on the retry still wins. If the hook-answer validator ever refused a policy hold, Rules would refuse instead (fail closed).
- **Bridge version:** holds need a bridge that carries the hold verdict (bridge 0.1.17 or later; the manifest declares `requires.bridge`). On an older bridge a hold is treated as a deny: the hold answer also carries `reason`, so the old bridge refuses the call with "Needs owner review: <reason>" (fail closed); nothing runs without the owner.
- **Context (`rules_context`):** `rules.narrowing` `{v, ruleId, reason, memoryTags {anyOf, noneOf}, deepDatasets {anyOf, noneOf}}` (Knowledge reads `memoryTags` and refuses a v 2; no app applies `deepDatasets` yet; a key no rule set is absent). `v` is 2 exactly when the merged narrowing has `deepDatasets` (spec 0.1.68), else 1: a reader that checks the version refuses v 2 (`narrowing_unsupported`) instead of answering unfiltered, `rules.matched`, `rules.onBehalfOf`.
- **After (`rules_filter`, reads only, 2000 ms):** redacts result objects whose `tags[]` fail the narrowing.
- **On behalf of:** the bridge copies the runner's claim into `tb.onBehalfOf` (unverified). Rules resolves it to Fleet teams; a claim can only make a decision stricter, never wider.
- **Fleet read model:** Governance (product id `fleet`) `directory_feed` (contract `fleet.directory_feed/1`, `sinceRevision`) through the companion grant, never inside a hook (Rules asks with `accept: ["agent_handles"]` for `agents[].handles`, Governance 0.3.0; a Governance that refuses `accept` with a 400, 0.2.x, is read without it at once and asked again after 10 minutes; the first read with `accept` onto a copy without handles is a full one): at start and every 60 s with an app-initiated call, on agent-list changes, and from owner pages when older than 60 s. Every answer is validated against the vendored schema (`src/contracts`) and every handle must satisfy `normalizeHandle(h) === h`; a mismatch is a refusal (error shown by `fleet_status`, nothing of the answer read). Fail closed (C230, C236): a refusal (no grant, not found, unlicensed, any 4xx, an invalid answer) clears the copy at once; a transient failure (5xx incl. the feed's 503 `feed_too_large`, timeout) keeps it only while the last successful read is 10 minutes old or less. While the copy is unavailable (never read, refused, too old), a **deny or hold** rule that names Fleet facts (`callerTeams`, `onBehalfOf.teams`, `onBehalfOf.trust`) **applies**, and an **allow** rule that names them does **not**. The Rules pages say "Governance data unavailable — team rules apply strictly".
- **Calls from apps (`callerProducts`, since 0.5.0; needs bridge 0.2.2 or later):** the hook call carries the calling instance's VERIFIED product (`caller.product`, from the bridge's signed config) for app callers. Caller identity: an app is identified by that product, never by a name, an input or context field or an instance id (an instance id changes on reinstall); an agent is identified by its agent id and never matches a rule that names `callerProducts` (deny, hold or allow). An app with no valid product (older bridge, unmapped caller) fails closed like unavailable Fleet facts: a deny or hold rule with `callerProducts` applies (trace detail `callerProductUnavailable`), an allow rule with it does not (its narrowing still applies). Writers refuse an invalid or repeated id and a combination with `modes`, `callerTeams` or agent-only `agents` that could never match an app. `rules_explain` reads an app's decisions by its verified product (older rows by instance id). Because the product is the identity, two live instances of the same product share one decision history in `rules_explain`: each sees the other's decisions. This is accepted (C237); decisions of another product, of an agent and of an app with no verified product (read by its own instance id) stay private. Writers also refuse a `callerProducts` id that is not in the signed app catalog (like `products`), and refuse every such rule with `catalog_unavailable` while Rules has no catalog; the Rules page flags a stored rule that names an unknown app "never matches".
- **Calling agent's trust (`callerTrust`, since 0.5.0, C373 D4b):** the trust of the CALLING agent from the Governance feed (agents[].trust, key `agent:<id>`). A Fleet fact like `callerTeams`: while the copy is unavailable a deny or hold rule with it applies and an allow rule does not; an allow needs the agent active (not blocked, not removed); an agent the directory does not know is `unreviewed`. An app caller has no agent trust, so a `callerTrust` rule never matches an app (writers refuse it next to `callerProducts` or `agents` that lists only apps).
- **Recipients (`recipients`, since 0.5.0, C373 D5, CONTRACT-RECIPIENTS; needs spec 0.1.81 / bridge cap `hook_recipients`):** who an outward call goes to, from the hook's `target.recipients` (canonical handles, at most 64; read structurally until the spec pin moves) and `target.recipientsIncomplete`. Each handle maps to its HOLDERS in the Governance copy (contacts by handle; agents by handle since Governance sends `agents[].handles`): their teams, their trust set, `known` = at least one holder (an unknown handle is `unreviewed`). Deny/hold: ANY recipient matches ALL the given sub-criteria. Allow: at least one recipient and EVERY recipient matches, every holder active. UNKNOWN recipients (absent: an older bridge, an op that declares none; `recipientsIncomplete`; a value that is not canonical; more than 64) fail closed: deny/hold apply (trace `recipientsUnknown`), allow never. `[]` (known: no recipients) matches no recipient rule. The rule needs `effects` exactly `["outward"]` (S2: every other call's recipients are unknown, so a deny/hold would catch them all) and at least one sub-criterion. Decisions keep the recipient COUNT (`detail.recipients`), never a handle. Email handles come with a future manifest `normalizeHandle` (`email:`).
- **Calls from workflows (`callerWorkflows`, since 0.5.0, C373 D2c, Evolution P1):** the VERIFIED workflow id of an app caller (hook `caller.workflow`, `^[a-z][a-z0-9-]{2,39}$`, read structurally until the spec pin has P1). Agents never match. Writers require `callerProducts` to include `evolution` (only Evolving Workflows runs workflows). A call WITHOUT a workflow (agreed with Evolution): when the bridge cap `app_workflow_grants` is visible, it is not a workflow call (no match); when it is not visible, a deny or hold rule applies to an `evolution` caller (trace `workflowUnavailable`) and an allow rule never matches. The SDK 0.1.40 hook context has no `bridgeCaps`, so `onStart` registers the start context's reader per database and the gate reads it from memory; caps never read count as not visible (the strict path). The trace keeps the workflow id (`detail.workflow`).
- **Missing facts and the default mode:** when the only rules that apply are closed ones (facts missing) and no rule matches on known facts after them, the stricter of that rule and the default mode decides: with the facts the call would reach the mode, so Closed never answers a hold where known facts get a refusal (C236 with C373c).
- **Default mode (C373c, since 0.5.0):** what the gate answers for a call that matches NO rule: `permissive` = allow (the default, also after an update), `verification` = hold for the owner (family `policy`, "Needs owner review: no rule covers this call (Verification mode)"; it lands in the target app's Holds and in the operator Inbox), `closed` = refuse ("Rules: no rule allows this call (Closed mode)"). Agents, apps and Evolution engine calls alike. A call that matches a rule is decided by it in every mode. The owner sets it on the Rules page (`mode_set`; a looser mode needs a confirm; every change is recorded). Built-in exemptions on the no-match path, shown as read-only "system" lines: Rules' own `fleet.directory_feed` read (verified product `rules` only), Operator Inbox's owner DMs through Connect (`buzz_dm`, `buzz_dm_first`, `channel_dm`, `channel_dm_first`; verified product `inbox` only, else a hold would DM the owner and the DM would be held again), Rules' own agent ops (`rules_explain`, `rule_draft_submit`, `draft_status`) and standard `tb.*` ops. The dry run shows what each mode would do.
- **Badge:** pending English drafts count toward the app's `pendingHolds` (TBD badge).
- **App catalog (since 0.2.7, writers strict):** at start and every 6 h (every minute after a failure) Rules reads the SIGNED release index that Core reads (platform `registry` release; JWS verified with the pinned release key, which is a copy of the platform `registry/keys.json`, so a release-key rotation needs a new Rules release; each manifest is checked against `manifestDigest` and `validateManifest`). Every writer (owner rule create/update, dry-run candidate, `rule_draft_submit`, draft apply) refuses a rule that can never match: an unknown app, an operation a named app does not declare (an MCP tool name such as `tools_call` gets "did you mean `tools`"), an owner-only (person) operation, or an effect the named operation never has (dynamic operations excepted: the bridge sends the resolved effect). Without any catalog yet, a rule that names apps is refused with `catalog_unavailable` (503). Stored rules and drafts are never deleted: the Rules page flags them "never matches", and such a draft cannot be applied (`draft_never_matches`, 409). The gate never reads the catalog. Unit tests set `TB_RULES_CATALOG_OFF=1`. The catalog is the only outbound call of the app (15 s timeout, 4 MB cap; outbound HTTPS to github.com).
- **English rules:** two ways in, both a draft only; the owner approves it on the Drafts page (`draft_decide`, C84). (1) The owner's own agent translates and calls `rule_draft_submit`. (2) The owner types the rule in the box at the top of the Rules page (C373, J3): `rule_compose` (person, read, no state) reads it with a deterministic parser (`src/compose.ts`: agent names from the agent directory, Governance team names, app ids from the catalog, the app that makes the call → `callerProducts`, effects and hold/refuse/allow words, memory-tag narrowing) and returns proposed rules, one readable line each, notes and what it could not read (a name not found or shared is never guessed); the owner edits or removes rules in the structured editor and `rule_compose_save` stores them as a draft with source `owner`. Every proposed rule passes the same writer checks as `rules_set` (schema, `specProblem`, the catalog). The parser sits behind a `Drafter` seam (`drafter: parser | model`). Optional model drafter (`src/model-drafter.ts`): only when the parser could not read everything, the bridge has cap `model_roles` and the owner bound the optional role `utility` (else `reasoning`), the owner's own model drafts the whole text as JSON; its rules go through the same checks plus a known-names check, it only ADDS rules to the parser's (every parser rule stays; a model allow with an empty match is refused; directory names reach it as quoted JSON data), and any failure falls back to the parser with a note. Negation is read exactly or the sentence is not read: words that forbid never become an allow. At approval every draft rule is placed again against the current rules, active and inactive (`src/placement.ts`); the Drafts page shows the final priority. Never in a hook. Rules never calls a model to decide; a model may only help draft.
- **Restore a revision (C373 Q-7):** every save, delete and restore adds a revision row; history is never rewritten. `rule_restore {ruleId, rev, expectedRev?}` (person, write, idempotency required) makes the spec of revision `rev` the current spec as a NEW revision (change `restored`, `from` = the copied revision, the owner recorded as actor). A deleted rule comes back into evaluation. The old spec passes the same writer checks as `rules_set` (catalog included); if it fails today, for example because the operation is gone from the app catalog, the restore is refused with the writer's reason. Restoring the current revision of a live rule is refused. UI: the editor's History section, and "Show deleted rules" with History on a deleted rule; "Restore this version" asks first.
- **Allow always, check against recent calls, text rules (C373 dev.5):** a hold card links to Rules with `?new=allow&product=&op=&hold=&agent=|callerProduct=` and the editor opens with a narrow allow rule placed before the hold rule and after any refuse rule that could match (nothing is saved before Save rule; a dynamic operation needs one tool). "Check against recent calls" runs an unsaved rule over the last recorded gate decisions (`rules_preview_recent`; recipient, caller-team and caller-trust rules cannot be checked). Every call that is not a read is recorded even when no rule matched. Writers refuse control and invisible characters (U+202E, U+200D, …) in titles, reasons, descriptions, draft text and notes. One unreadable app manifest is named on the Rules page and does not fail the catalog.
- **Access page (C374, since 0.5.1):** one row per agent and per app (Rules itself is not offered). The owner sets how deep it may go (Nothing, Read only, Read and change, Also outward, Also money, Everything: each level adds one effect in the order read, write, outward, money, destructive), what happens beyond that (hold or refuse), and optionally only some apps (the others are refused) and only some tools of connected services (other tools of those apps' dynamic operations are refused). It is saved as ordinary rules at priority 900 and up (`src/ui/access-model.ts`), so the owner's own rules decide first and the default mode no longer decides for that caller; the setting is read back from the rules' description (`access/1`), a hand edit is flagged, "Check" runs `rules_preview` per effect. An agent keeps Rules' own `rules_explain`, `rule_draft_submit`, `draft_status`; Inbox keeps its owner DMs. An app added to the catalog after the save is outside the app limit until the setting is saved again (the level still applies).
- **Templates (C373 Q-9):** "Start from a template" (empty state and next to New rule) offers starter rules: hold an agent's outward actions, hold all money actions, block destructive actions for bound agents, hold outward actions of a team (only while Governance teams are known), and hold an app's outward actions (`callerProducts`, only while the app catalog lists apps). The owner picks the one parameter (agent or team); the editor opens prefilled and the rule is saved with `rules_set` as usual. Nothing is active by default and a template never saves by itself (`src/ui/templates.ts`, pure data).

## Develop

```sh
corepack enable && pnpm install --frozen-lockfile --ignore-scripts   # commit pnpm-lock.yaml: CI installs with --frozen-lockfile
# typecheck, test, conformance, build and start first run `tb-gen kit` (op ids + I/O types from the manifest)
pnpm typecheck && pnpm lint && pnpm test
pnpm build            # kit, server to dist/, UI to dist/ui
pnpm conformance      # SDK conformance suite against this app (not release evidence; QA is)
TB_STANDALONE=1 TB_DATA_DIR=.data pnpm start   # app-alone mode: person UI only, no agent calls (operations answer 503 no_bridge)
```

## Environment

The SDK reads only `TB_*` variables (SDK API section 13). The Dockerfile defaults `TB_DATA_DIR=/data` (the `data` volume mount) and `TB_BACKUP_DIR=/data/backup` (one volume per service). The deploy recipe sets the rest: `TB_INSTANCE_ID`, `TB_ENROL_CODE`, `TB_BRIDGE_URL`, `TB_PORTAL_KEYS`, `TB_KEK`. Optional: `TB_LOG_LEVEL`, `TB_RESTORE_FROM`, `TB_STANDALONE`. The listen port is the manifest `runtime.port`.

Before its first claim the SDK checks that `TB_DATA_DIR` is a mounted volume; on a container's own disk it waits and does not use the enrolment code. Tests and CI that run `startApp` or `tb-exec` in bridge mode on Linux set `TB_DATA_EPHEMERAL=1` in that test or CI step (the conformance suite sets it itself; this repository's unit tests run app-alone and need none). Never set it in a deploy recipe.

## Release

1. Set the same version in `package.json` and `tealbrick.manifest.json`.
2. Tag `v<semver>` (for example `v0.2.11`) on a green pipeline and push the tag. Tags are immutable.
3. The release Action builds and pushes the GHCR image and the kit tarball, then writes the signed release record from the manifest. `registry-sync` signs the index entry with the image digest and the manifest digest.
4. Core deploys the newest stable version when the owner installs or updates the app. Core (E3, live since RS-3) switches to the new version only after a health check and rolls back when it fails, restoring the pre-update data snapshot; the gate is "not worse than before" (C219). The full effect needs the app to run SDK 0.1.25, which holds for the dev channel builds today and for stable after their promotion.

Check `publisher` and `source.repo` in the manifest. The repository name must match the image name in `tealbrick-ci.json` (`opt2-tealbrick-rules`).
## Dependency pins and caching

- `@opt2-tealbrick/*` dependencies are pinned as tarball URLs on the dist host (`Tealbrick/opt2-tealbrick-dist` releases). `pnpm-lock.yaml` carries the sha512 integrity of every such tarball. After changing one, run `pnpm install`, then `node <opt2-tealbrick-platform>/ci/tb-ci.ts pin-tarballs .`, then `pnpm install --frozen-lockfile`, and commit the lockfile. Image builds run `pnpm install --frozen-lockfile --ignore-scripts`.
- `pnpm build` writes the UI to `dist/ui/index.html` + `dist/ui/assets-<content hash>/`; the SDK serves `index.html` as `no-cache` and the hashed directory as immutable, so a deploy is visible at once.
